# Pocketch 구현 계획

## 1. 구현 원칙

Pocketch는 한 대의 노트북과 최신 데스크톱 Chrome에서 완결되는 정적 웹 애플리케이션으로 구현한다. React는 화면과 사용자 흐름을, Phaser와 Matter Physics는 실시간 물리 장면을 담당한다. 촬영 이미지와 게임 결과는 IndexedDB에 저장하며 별도 애플리케이션 서버를 두지 않는다.

초기 구현에서 먼저 검증할 위험 요소는 다음 두 가지다.

- 브라우저 배경제거 라이브러리의 처리 속도, 메모리 사용량, 모델 배포 방식과 라이선스
- 아이템이 누적될 때 물리 장면을 일괄 축소하고 재배치하는 과정의 안정성

두 기능은 전체 화면 흐름과 결합하기 전에 작은 기술 검증으로 확인한다. 검증 결과는 설정값과 구현 선택에 반영하되 제품 명세의 사용자 흐름과 데이터 모델은 유지한다.

## 2. 애플리케이션 구조

예상 소스 구조는 다음과 같다.

```text
src/
  app/                  # 앱 초기화, 모드 전환, 공통 레이아웃
  components/           # 버튼, 모달, 상태 및 오류 표시
  domain/               # 데이터 모델, 축소·점수·랭킹 규칙
  engine/               # Phaser 게임 설정, 장면, 물리 바디
  features/
    collection/         # 촬영, 등록, 상세, 삭제
    game/               # 닉네임 입력, 게임 HUD, 결과
    ranking/            # 상위 10위 조회와 초기화
  services/
    camera/             # 카메라 권한과 스트림 수명 주기
    image-processing/   # 배경제거, 크롭, 리사이즈, WebP 변환
    storage/            # IndexedDB 스키마와 저장소
```

React와 Phaser는 명시적인 명령과 이벤트로 통신한다. 프레임마다 바뀌는 좌표와 속도는 Phaser 내부에 두고, React에는 점수, 남은 시간, 선택한 물건과 같은 화면 상태만 전달한다. 이를 통해 잦은 React 렌더링이 물리 프레임에 영향을 주지 않게 한다.

애플리케이션 모드는 URL 라우팅 대신 `collection`, `game`, `ranking` 상태로 전환한다. 게임 진행 중 다른 모드로 이동할 때는 확인 절차를 거치고, 확인한 경우 현재 판을 종료하되 완료 결과로 저장하지 않는다.

## 3. 단계별 구현

### 3.1 프로젝트 기반과 공통 UI

Vite, React와 TypeScript 프로젝트를 구성하고 Phaser 3, Matter Physics, IndexedDB 래퍼, 테스트 도구를 설치한다. 검은 배경의 반응형 셸, 세 모드 내비게이션, 공통 버튼과 모달, 오류 안내 영역을 만든다.

이 단계에서 다음 항목을 완료한다.

- 데스크톱 Chrome 기준의 반응형 레이아웃과 전체 화면 대응
- 키보드 포커스가 가능한 주요 버튼과 명확한 포커스 표시
- 모달 열기·닫기와 포커스 복귀
- 창 크기 변경을 Phaser 장면에 전달하는 공통 연결부
- 사용자에게 복구 방법과 재시도 동작을 함께 제공하는 오류 모델

### 3.2 IndexedDB 저장소

제품 명세의 `CollectedItem`, `CollectionSettings`, `GameResult` 모델을 기준으로 데이터베이스를 구성한다. 저장소 접근은 하나의 모듈에서 캡슐화하고 스키마 버전과 마이그레이션 진입점을 둔다.

저장소는 다음 연산을 제공한다.

- 물건 전체 조회, 추가, 개별 삭제, 전체 삭제
- 채집 축소 설정 조회와 갱신
- 게임 결과 추가, 상위 10개 조회, 전체 삭제
- 채집 전체 초기화 시 물건과 축소 설정을 하나의 트랜잭션으로 초기화

랭킹은 점수 내림차순으로 정렬하고, 동점이면 `playedAt`이 이른 결과를 우선한다. 저장 실패는 메모리 상태에 성공한 것처럼 반영하지 않는다. 이미지 디코딩에 실패한 항목은 제외하고 나머지 데이터는 계속 불러온다.

### 3.3 촬영, 이미지 처리와 등록

촬영 흐름은 `카메라 준비 → 실시간 미리보기 → 촬영 확인 → 배경제거 처리 → 결과 등록` 상태로 구현한다. 각 상태가 허용하는 동작을 제한해 배경제거 중복 실행과 취소 후 저장을 방지한다.

카메라는 `navigator.mediaDevices.getUserMedia`를 사용한다. 권한 거부, 카메라 없음, API 미지원 상태에는 원인과 재시도 방법을 표시한다. 촬영 화면을 떠나면 미디어 트랙을 정지한다.

이미지 처리 파이프라인은 다음 순서로 실행한다.

1. 촬영 프레임을 메모리의 이미지 데이터로 변환한다.
2. 클라이언트 배경제거 라이브러리로 알파 채널을 생성한다.
3. 알파 영역을 기준으로 투명 여백을 제거한다.
4. 긴 변이 1024px을 넘으면 비율을 유지해 축소한다.
5. 알파 채널을 유지하는 WebP Blob과 최종 너비·높이를 만든다.
6. 필수 이름과 선택 설명을 결합해 IndexedDB에 저장한다.

저장 또는 취소 후에는 카메라 원본, 임시 캔버스와 Object URL을 폐기한다. 배경제거 실패 시 원본은 저장하지 않고 재시도와 취소만 제공한다.

### 3.4 물리 채집 장면

Phaser 장면은 저장된 물건을 불러와 현재 `globalScale`에 맞게 물리 오브젝트로 만든다. 새 물건은 좌우 경계와 자신의 크기를 고려한 안전한 임의 위치에서 생성한다.

초기 충돌 바디는 투명 여백을 제거한 이미지 경계를 기준으로 단순한 사각형이나 볼록 다각형을 사용한다. 실제 대표 이미지로 겹침 정도와 성능을 비교한 뒤 더 정밀한 알파 윤곽 바디가 필요한지 결정한다.

축소 제어기는 다음 규칙을 독립적으로 관리한다.

1. 새 물건을 추가하고 물리가 안정될 때까지 기다린다.
2. 더미 최고점이 화면 높이의 25% 선을 넘는지 확인한다.
3. 넘었으면 해당 추가 작업에서 `scaleLevel`을 한 번만 증가시킨다.
4. `globalScale = 0.7 ** scaleLevel`로 계산한다.
5. 기존 물건의 이미지와 충돌 바디를 같은 비율로 갱신한다.
6. 중심점을 화면 크기에 비례해 재배치하고 경계 안으로 보정한다.
7. 변경한 설정을 IndexedDB에 저장하고 물리를 다시 안정화한다.

창 크기가 바뀌면 바닥과 좌우 경계를 재생성하고 물건을 새 크기에 비례해 재배치한다. 새로고침 시에는 저장된 축소 단계를 복원한 뒤 물건 더미를 다시 구성한다. 좌표 자체는 MVP 데이터 모델에 추가하지 않는다.

포인터를 600ms 이상 유지하면 상세 모달을 열고, 이동 거리가 임계값을 넘거나 포인터가 취소되면 길게 누르기를 취소한다. 렌더링 크기와 별도로 최소 44px 히트 영역을 유지한다. 개별 삭제는 확인 후 IndexedDB와 현재 장면에 모두 반영한다.

### 3.5 캐치 게임

게임 상태는 `idle`, `countdown`, `playing`, `paused`, `finished`로 구분한다. 시작 시점에 저장된 물건 목록을 스냅샷으로 보관해 플레이 도중 채집 데이터가 바뀌어도 현재 판에 영향을 주지 않게 한다.

게임 규칙은 다음과 같이 구현한다.

- 공백을 제거한 닉네임이 없거나 등록 물건이 없으면 시작을 막는다.
- 3초 카운트다운 뒤 30초 타이머와 아이템 생성을 시작한다.
- 스냅샷의 모든 물건에서 균등하게 무작위 선택하며 중복 등장을 허용한다.
- 방향키와 `A/D`를 누르는 동안 바구니를 이동한다.
- 반대 방향 키를 함께 누르면 가장 최근에 누른 방향을 사용한다.
- 바구니 충돌은 아이템당 한 번만 처리하고 100점과 획득 효과를 적용한다.
- 바닥으로 지나간 아이템은 점수 변화 없이 제거한다.
- 남은 시간이 0이면 생성을 멈추고 즉시 결과 상태로 전환한다.

`visibilitychange`와 창 포커스 변화를 감지해 타이머, 생성기와 물리를 함께 일시정지한다. 이때 눌린 키 상태를 초기화한다. 돌아오면 안내 화면에서 사용자가 재개하도록 한다. 창 크기 변경은 장면 경계와 바구니 위치만 보정하고 점수와 남은 시간은 유지한다.

완료 전환은 한 번만 실행되도록 보호한다. 완료된 결과만 IndexedDB에 저장하고 닉네임, 최종 점수, 획득 개수를 결과 화면에 표시한다.

### 3.6 랭킹과 관리 기능

랭킹 화면은 상위 10개의 순위, 닉네임, 점수와 플레이 시각을 표시한다. 결과가 없을 때는 빈 상태를 보여준다. 랭킹 전체 삭제와 채집 전체 초기화는 서로 독립적인 확인 절차를 사용한다.

등록 물건이 없을 때 게임 시작 버튼을 비활성화하고 채집 모드로 이동하는 안내를 제공한다. 저장 공간 부족 오류에서는 기존 물건의 상세·삭제 화면으로 이동할 수 있게 한다.

## 4. 테스트 전략

### 4.1 단위 테스트

브라우저 API와 물리 엔진에 의존하지 않는 규칙을 우선 검증한다.

- 이름과 닉네임에서 공백만 입력한 값을 거부하는지 확인
- 축소 단계별 배율이 `1 → 0.7 → 0.49 → 0.343`으로 계산되는지 확인
- 한 번의 물건 추가에서 축소가 한 단계만 증가하는지 확인
- 충돌당 100점, 놓친 물건 무감점, 시간 종료 후 점수 불변 확인
- 점수와 기록 시각에 따른 랭킹 정렬 및 상위 10개 제한 확인

### 4.2 저장소 테스트

실제 IndexedDB와 같은 동작을 제공하는 테스트 환경에서 물건, 설정과 결과의 추가·조회·삭제를 검증한다. 데이터베이스 업그레이드, 트랜잭션 실패, 채집 전체 초기화와 잘못된 이미지 항목 제외도 확인한다.

### 4.3 브라우저 통합 테스트

카메라와 배경제거는 브라우저 수동 검증을 포함하고, 나머지 흐름은 가능한 범위에서 자동화한다.

- 카메라 권한 승인·거부, 재촬영, 처리 실패와 재시도
- 저장 후 새로고침 시 이미지, 메타데이터와 축소 단계 복원
- 길게 누르기, 상세 모달, 개별 삭제와 전체 초기화
- 게임 중 포커스 상실, 모드 이탈과 창 크기 변경
- 결과 저장, 랭킹 유지와 전체 삭제

물리 검증은 대표 이미지와 고정 난수를 사용해 재현 가능하게 만든다. 대표 이미지 18~22개가 화면 높이의 약 75%를 채우는지를 기준으로 초기 아이템 크기를 조정하고, 임계선 판정 자체는 더미의 실제 최고점으로 수행한다.

### 4.4 현장 검증

최신 Chrome과 내장 카메라가 있는 실제 노트북에서 촬영부터 랭킹까지 전체 흐름을 수행한다. 작은 창, 일반 창과 전체 화면에서 UI와 물리 경계를 확인하고, 최소 100개의 저장 이미지로 프레임 유지, 메모리 사용과 게임 시작 시간을 측정한다.

## 5. 구현 순서와 완료 조건

| 단계 | 주요 결과물 | 완료 조건 |
| --- | --- | --- |
| 1. 기반 | Vite 앱, 공통 레이아웃, 모드 전환 | 세 모드 전환과 반응형 셸이 동작함 |
| 2. 저장소 | IndexedDB 스키마와 저장소 API | 물건·설정·결과가 새로고침 후 복원됨 |
| 3. 촬영 | 카메라, 배경제거, 등록 폼 | 촬영물이 투명 WebP로 저장됨 |
| 4. 채집 | 물리 더미, 축소, 상세·삭제 | 더미와 반복 축소가 안정적으로 동작함 |
| 5. 게임 | 카운트다운, 입력, 점수, 일시정지 | 30초 게임과 예외 흐름이 완료됨 |
| 6. 랭킹 | 결과 저장과 상위 10위 | 정렬·보존·초기화가 명세와 일치함 |
| 7. 통합 검증 | 브라우저·현장 테스트 | 제품 명세의 완료 기준을 모두 통과함 |

낙하 간격, 중력, 바구니 속도와 크기처럼 제품 명세에 정확한 수치가 없는 값은 중앙 설정 모듈에 모은다. 대표 이미지와 실제 현장 장비에서 플레이한 결과로 조정하고, 도메인 규칙에 하드코딩하지 않는다.

## 6. 주요 결정 사항

- 정적 호스팅에서도 새로고침 문제를 피하도록 URL 기반 서버 라우팅을 사용하지 않는다.
- 카메라 접근을 위해 배포 환경은 HTTPS를 전제로 한다.
- 물리 좌표는 영속화하지 않고 저장된 물건과 축소 단계에서 장면을 재구성한다.
- 게임은 시작 시 아이템 풀을 스냅샷으로 고정한다.
- 물리와 타이머는 포커스 상실 시 함께 멈추고 사용자 안내 후 재개한다.
- 성능과 저장 공간에는 강제 아이템 수 제한을 두지 않고 오류와 관리 동선을 제공한다.
